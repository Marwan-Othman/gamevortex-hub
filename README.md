# GameVortex Hub — Production Build Edition

GameVortex Hub is a Next.js + React + TypeScript application backed by PostgreSQL through Prisma. This repository is the existing project, upgraded for repeatable production validation rather than a separate demo.

## Stack

- Next.js 15 + React 19 + TypeScript
- Prisma 6 + PostgreSQL
- Zod server-side validation
- HttpOnly signed sessions with scrypt password hashing
- Server-side RBAC for owner/admin surfaces
- Security headers, Origin checks and API rate limiting
- Vortex Score, gamer profiles, XP/achievements, social activity, library, reviews, marketplace and moderation foundations

## Dependencies

Runtime dependencies are declared in `package.json`:

- `next`
- `react`
- `react-dom`
- `@prisma/client`
- `zod`

Development/build dependencies:

- `prisma`
- `typescript`
- `@types/node`
- `@types/react`
- `@types/react-dom`

There are no hidden npm dependencies. Do not copy `node_modules` between machines; install from `package.json`.

## First install

Use Node.js 20 LTS or 22 LTS and npm 10+.

```bash
npm install
```

`postinstall`/the build pipeline generates the Prisma client. If you prefer an explicit command:

```bash
npm run db:generate
```

After the first successful `npm install`, commit the generated `package-lock.json` to the repository. Production CI should then use:

```bash
npm ci
```

The lock file is intentionally generated by npm from the exact registry state used by your CI environment; it should not be hand-written.

## Environment

Copy `.env.example` to `.env` for local development. Production must provide at least:

- `DATABASE_URL`
- `AUTH_SECRET` (32+ random characters; use a secret manager)
- `APP_ORIGIN` (HTTPS in production)

Payment webhooks additionally require `PAYMENT_WEBHOOK_SECRET` when a payment provider is enabled.

Generate a secret with:

```bash
openssl rand -base64 48
```

Never commit `.env`, production credentials, API keys, payment secrets or wallet secrets.

## Prisma: local development

Validate the schema:

```bash
npm run db:validate
```

Generate the client:

```bash
npm run db:generate
```

Create/apply a development migration when the schema changes:

```bash
npx prisma migrate dev --name describe_your_change
```

The repository now contains a baseline production migration at:

```text
prisma/migrations/20260814190000_init/migration.sql
```

and `migration_lock.toml` is tracked. This is required for `prisma migrate deploy` to be meaningful in production.

## Complete production build

The supported validation pipeline is:

```bash
npm ci
npm run build:production
npm start
```

`build:production` performs, in order:

1. Production environment validation.
2. `prisma validate`.
3. `prisma generate`.
4. `prisma migrate deploy` against the configured PostgreSQL database.
5. TypeScript type checking.
6. `next build`.
7. Production smoke validation, including the generated `.next/BUILD_ID`.

The normal application build is also available:

```bash
npm run build
```

It performs `prisma generate` followed by `next build`.

## What counts as a successful production validation?

A release is considered build-validated only when all of these succeed:

```text
npm ci
        ↓
Prisma schema validation
        ↓
Prisma client generation
        ↓
Prisma migrations deployed successfully
        ↓
TypeScript typecheck
        ↓
Next.js production build
        ↓
Smoke check + .next/BUILD_ID
        ↓
npm start
```

A successful `next build` alone is **not** enough: it does not prove that the production database is reachable, migrations are applied, secrets are configured, payment webhooks are working, or external providers are connected.

## Important production behavior

Database-backed pages are marked `force-dynamic` where appropriate so the production build does not attempt to query a developer database while compiling the application. Database access happens at request time. This makes CI builds independent of the production database while `prisma migrate deploy` remains an explicit deployment step.

The public sitemap is also generated dynamically from the database.

## External integrations

The project deliberately does not fake external integrations. Payment, payout/blockchain, AI, gaming-account import, email/push and external game/audio sources require real provider credentials and provider-specific adapters.

Do not mark an integration as production-ready merely because its interface exists. A provider is production-ready only after:

- real credentials are configured in a secret manager;
- OAuth/state/signature validation is enabled where applicable;
- webhook events are authenticated and idempotent;
- retry/reconciliation behavior is tested;
- provider rate limits are respected;
- failure paths are observable;
- a staging transaction has been verified end-to-end.

## Owner Points

- Default conversion: 30 points = 1 USD.
- Default minimum withdrawal: 15 points = 0.50 USD.
- A withdrawal is not automatically marked paid/settled.
- Real payout settlement must be implemented and verified with the selected provider before enabling withdrawals in production.

## Rate limiting

The current limiter is process-local memory. It is suitable for development and a single-instance deployment, but it is not a distributed rate limiter. For a multi-instance production deployment, replace it with a shared store such as Redis/Upstash before treating the deployment as horizontally scalable.

## Production checklist

- [ ] `npm ci` succeeds from a committed `package-lock.json`.
- [ ] `DATABASE_URL` points to the intended PostgreSQL instance.
- [ ] `AUTH_SECRET` is a strong secret of at least 32 characters.
- [ ] `APP_ORIGIN` is the real HTTPS origin.
- [ ] `prisma migrate deploy` succeeds.
- [ ] `npm run typecheck` succeeds.
- [ ] `next build` succeeds.
- [ ] `npm run test:smoke` succeeds and detects `.next/BUILD_ID`.
- [ ] `npm start` starts successfully.
- [ ] `/api/health` reports database health.
- [ ] Admin authentication/RBAC has been tested with real accounts.
- [ ] Payment webhook signatures have been tested with the real provider in staging.
- [ ] Payout/withdrawal settlement has been tested before enabling withdrawals.
- [ ] External game/audio sources are verified and licensed before publishing.
- [ ] Monitoring/logging and backups are configured.
- [ ] Distributed rate limiting is configured before horizontal scaling.
