# دليل التحقق المرحلي لـ GameVortex Hub

> **الغرض:** تشغيل نسخة مرحلية آمنة لاختبار البناء والهجرات والكتالوج والدفع وتسليم مفاتيح الألعاب. لا تستخدم هذا الدليل مع مفاتيح دفع حيّة أو مفاتيح ألعاب حقيقية قبل اكتمال المراجعة القانونية والتشغيلية.

## 1. المتطلبات

يلزم توفر نطاق HTTPS مخصص للبيئة المرحلية، وقاعدة PostgreSQL فارغة، وحساب دفع في وضع الاختبار فقط. يجب أن يكون نطاق staging منفصلًا عن نطاق الإنتاج، وأن تكون قاعدة بياناته ونسخه الاحتياطية منفصلة تمامًا.

| العنصر | المطلوب |
|---|---|
| Node.js | الإصدار 22 أو أحدث ضمن نطاق المشروع |
| قاعدة البيانات | PostgreSQL 16 أو متوافق معه |
| HTTPS | عنوان عام ثابت للبيئة المرحلية |
| الدفع | حساب اختبار لدى مزود واحد فقط |
| البريد | اختياري؛ استخدم بريدًا اختباريًا إن فُعّل |
| مخزون المفاتيح | مفاتيح اختبار فقط، وليست مفاتيح يمكن بيعها |

## 2. إعداد متغيرات البيئة

انسخ `.env.production.example` إلى `.env.production` في بيئة staging فقط. لا ترفع الملف إلى Git أو تشاركه في الرسائل أو السجلات.

```bash
cp .env.production.example .env.production
```

اضبط المتغيرات التالية بقيم مختلفة تمامًا عن الإنتاج:

```dotenv
NODE_ENV=production
APP_ORIGIN=https://staging.example.com
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/gamevortex_staging
AUTH_SECRET=ضع_قيمة_عشوائية_طويلة_لا_تقل_عن_32_حرفا
OWNER_EMAIL=owner-staging@example.com
OWNER_INITIAL_PASSWORD=كلمة_مرور_قوية_خاصة_بالبيئة_المرحلية
PAYMENT_PROVIDER=stripe
STRIPE_SECRET_KEY=مفتاح_اختبار_فقط
PAYMENT_WEBHOOK_SECRET=سر_Webhook_الخاص_بالاختبار
DIGITAL_KEY_ENCRYPTION_SECRET=قيمة_عشوائية_مستقلة_لا_تقل_عن_32_حرفا
RATE_LIMIT_STORE=upstash
UPSTASH_REDIS_REST_URL=عنوان_خدمة_الحدود
UPSTASH_REDIS_REST_TOKEN=رمز_خدمة_الحدود
```

أنشئ الأسرار محليًا، ولا تعيد استخدامها بين staging والإنتاج:

```bash
openssl rand -base64 48
```

## 3. التثبيت والتحقق قبل التشغيل

نفذ الأوامر الآتية من مجلد المشروع. يجب أن تنجح كلها قبل نشر التطبيق أو تسجيل Webhook.

```bash
npm ci
npm audit --omit=dev --audit-level=high
npm run validate:env
npm run db:validate
npm run db:migrate
npm run db:generate
npm run typecheck
npm test
npm run build
```

بعد تطبيق الهجرات، نفذ:

```bash
npm run db:status
```

يجب أن تظهر رسالة أن مخطط قاعدة البيانات محدث. لا تستخدم `prisma migrate dev` في staging أو الإنتاج.

## 4. تجهيز بيانات اختبار المتجر

ابدأ بمنتج واحد فقط من نوع `GAME_KEY` وتسليم `CODE`. يجب أن تكون اللعبة منشورة وحالة مصدرها `VERIFIED` أو `OFFICIAL_SOURCE`، ويجب أن يكون `supplierVerified=true` للمنتج. لا تظهر المنتجات التي لا تستوفي هذه الشروط للعميل ولا يمكن طلبها من API.

بعد إنشاء المنتج، استورد مفاتيح اختبار عبر واجهة المالك فقط:

```http
POST /api/admin/products/<PRODUCT_ID>/keys
Content-Type: application/json

{
  "codes": [
    "STAGING-TEST-KEY-001",
    "STAGING-TEST-KEY-002"
  ]
}
```

لا ترسل مفاتيح حقيقية عبر أدوات المتصفح المفتوحة أو ملفات JSON محفوظة. يحفظ التطبيق المفاتيح بصيغة مشفرة، ويخزن fingerprint لمنع الاستيراد المتكرر.

## 5. إعداد مزود الدفع الاختباري

سجّل عنوان Webhook العام التالي في بيئة الاختبار لدى المزود:

```text
https://staging.example.com/api/payments/webhook
```

في حالة Stripe، يلزم endpoint HTTPS عام وتوقيع الطلب باستخدام raw request body ورأس `Stripe-Signature`. كما يجب التعامل مع إعادة التسليم وعدم افتراض ترتيب الأحداث.[1]

اشترك على الأقل في الأحداث التالية:

| الحدث | الغرض داخل GameVortex |
|---|---|
| `checkout.session.completed` | تأكيد الدفع وتسليم المفاتيح |
| `checkout.session.async_payment_succeeded` | تأكيد دفع غير متزامن عند نجاحه |
| `checkout.session.async_payment_failed` | وضع الطلب في حالة فشل |
| `charge.refunded` | إلغاء المفتاح والامتياز المرتبطين بالطلب |

> لا تعتمد على صفحة العودة من الدفع لتسليم المنتج. التسليم يحدث فقط بعد Webhook موقع وصالح من مزود الدفع.[1]

## 6. سيناريو اختبار إلزامي

اختبر التسلسل التالي بحساب مستخدم staging جديد ومفتاح دفع اختباري:

1. أنشئ مستخدمًا جديدًا وسجّل دخوله.
2. افتح `/marketplace` وتحقق من ظهور المنتج المؤهل فقط.
3. اضغط «شراء الآن» وانتقل إلى Checkout الاختباري.
4. أكمل الدفع الاختباري.
5. تحقق من وصول Webhook ناجح من لوحة المزود وسجل التطبيق.
6. افتح `/orders` وتأكد من أن الطلب أصبح `COMPLETED`.
7. اضغط «عرض مفاتيح اللعبة» وتأكد من ظهور المفتاح الصحيح فقط.
8. أعد إرسال Webhook الناجح نفسه من لوحة المزود؛ يجب ألا يتغير المخزون أو يظهر مفتاح جديد.
9. نفذ Refund اختباري وتحقق من وضع الطلب `REFUNDED` وإلغاء المفتاح والامتياز.
10. حاول شراء منتج غير موثق أو معطل أو بلا مخزون؛ يجب أن يرفض الخادم الطلب.

## 7. مؤشرات القبول قبل الإطلاق المحدود

| المعيار | نتيجة مطلوبة |
|---|---|
| بناء التطبيق | نجاح `npm run build` |
| تدقيق الاعتمادات | لا توجد ثغرات عالية أو حرجة |
| الهجرات | تنجح على قاعدة فارغة وعلى نسخة staging |
| Webhook | ينجح التحقق من التوقيع ورفض التوقيع الخاطئ |
| عدم التكرار | إعادة الحدث لا تسلم مفتاحًا إضافيًا |
| المخزون | لا يمكن بيع عدد أكبر من المفاتيح المتاحة |
| الاسترداد | إلغاء المفتاح والامتياز المرتبطين بالطلب |
| النسخ الاحتياطي | تجربة استعادة ناجحة على قاعدة منفصلة |
| المراقبة | تسجيل أخطاء Webhook والتنبيه عند فشل التسليم |

## 8. ممنوعات قبل الإنتاج

لا تفعّل الدفع الحي، ولا تضع مفاتيح ألعاب حقيقية، ولا تفتح تسجيل الموردين، ولا تشغّل السحوبات أو الإحالات أو السحوبات المالية للمالك قبل إتمام عناصر القبول أعلاه ومراجعة الشروط القانونية والاسترداد والدعم.
