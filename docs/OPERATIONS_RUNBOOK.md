# دليل التشغيل والمراقبة — GameVortex Hub

## نطاق هذا الدليل

هذا الدليل مخصص لبيئة **staging** ثم للإطلاق المحدود بعد نجاحها. لا يعتبر بديلًا عن مراقبة مستضافة أو عقد مستوى خدمة؛ بل يحدد الحد الأدنى التشغيلي الذي يجب تنفيذه قبل فتح المتجر للجمهور.

## الفحص اليومي

نفّذ هذه الفحوص مرة يوميًا في staging، وبعد أي نشر أو تغيير في متغيرات البيئة:

| الفحص | الأمر أو الإجراء | النتيجة المطلوبة |
|---|---|---|
| حالة الحاويات | `docker compose -f docker-compose.prod.yml ps` | `postgres` و`app` بحالة healthy |
| فحص الصحة العام | `curl -fsS https://STAGING_DOMAIN/api/health` | `status: ok` و`database: up` فقط |
| سجل التطبيق | `docker compose -f docker-compose.prod.yml logs --since=24h app` | لا أخطاء متكررة أو فشل اتصال بقاعدة البيانات |
| سجل قاعدة البيانات | `docker compose -f docker-compose.prod.yml logs --since=24h postgres` | لا أخطاء إعادة تشغيل أو امتلاء مساحة |
| تدقيق الحزم | `npm audit --omit=dev --audit-level=high` | لا ثغرات عالية أو حرجة |
| الهجرات | `npm run db:status` | مخطط القاعدة محدث |

لا يتضمن endpoint العام أي تفاصيل عن مفاتيح الخدمات أو تهيئتها. يمكن للمالك فقط طلب فحص إداري مصادق عليه عبر الرأس `x-admin-health: 1` من جلسة مالك صالحة.

## النسخ الاحتياطي والاستعادة

### النسخ الاحتياطي

شغّل نسخة احتياطية مشفرة أو مخزنة في موقع وصوله مقيد. ينشئ البرنامج ملفًا مؤقتًا ولا ينشر ملفًا نهائيًا إذا فشل `pg_dump`.

```bash
POSTGRES_CONTAINER=gamevortex-postgres \
POSTGRES_USER=gamevortex \
POSTGRES_DB=gamevortex \
npm run db:backup -- ./backups/gamevortex-$(date +%Y%m%d-%H%M%S).sql.gz
```

تحقق من الملف قبل نقله إلى التخزين المخصص:

```bash
gzip -t ./backups/gamevortex-YYYYMMDD-HHMMSS.sql.gz
```

### اختبار الاستعادة

اختبر الاستعادة شهريًا على قاعدة بيانات منفصلة تمامًا عن staging والإنتاج:

```bash
gunzip -c ./backups/gamevortex-YYYYMMDD-HHMMSS.sql.gz | \
  psql "$RESTORE_DATABASE_URL"
```

بعد الاستعادة، نفذ `npm run db:status` باستخدام `RESTORE_DATABASE_URL` ثم افحص عدد الجداول والطلبات دون كشف أي مفاتيح رقمية في السجل.

## مراقبة الدفع والتسليم

راقب مزود الدفع ولوحة Webhook في وضع الاختبار. عالج أي فشل Webhook قبل إعادة المحاولة اليدوية.

| الإشارة | الإجراء الفوري |
|---|---|
| Webhook بتوقيع غير صالح | تحقق من `PAYMENT_WEBHOOK_SECRET` ولا تسجل body أو التوقيع في ملفات عامة |
| طلب مدفوع بلا مفاتيح | أوقف المنتج، تحقق من مخزون `AVAILABLE`، ثم راجع الحدث والطلب |
| تكرار Webhook | لا تعالج الطلب يدويًا قبل التأكد من حالة `Payment` و`DigitalKey`؛ التطبيق مصمم لمنع التسليم المزدوج |
| استرداد | تحقق من أن الطلب `REFUNDED` والمفتاح `REVOKED` والامتياز ملغى |
| فشل قاعدة البيانات | أوقف الدفع مؤقتًا، استعد الخدمة، ثم أعد تشغيل الأحداث غير المسلّمة من مزود الدفع |

## قواعد التعامل مع الأسرار

لا تسجل أو تشارك أو تضع في Git القيم التالية: `DATABASE_URL` و`AUTH_SECRET` و`STRIPE_SECRET_KEY` و`PAYMENT_WEBHOOK_SECRET` و`DIGITAL_KEY_ENCRYPTION_SECRET` أو أكواد مفاتيح الألعاب الخام. عند تبديل `DIGITAL_KEY_ENCRYPTION_SECRET`، يجب تنفيذ خطة تدوير محددة؛ فقدان القيمة القديمة يمنع فك المفاتيح المخزنة بها.

## قرار الإطلاق المحدود

لا تنتقل من staging إلى إطلاق محدود إلا إذا تحققت هذه الشروط في يومين متتاليين على الأقل:

1. جميع بوابات CI ناجحة، بما فيها الهجرات والاختبارات والبناء وفحص الدخان.
2. نجحت عملية شراء اختبارية واسترداد اختبارية وإعادة تسليم Webhook دون تكرار مفتاح.
3. نجح اختبار الاستعادة من نسخة احتياطية منفصلة.
4. لا توجد أخطاء متكررة في السجلات خلال 24 ساعة.
5. تم اعتماد سياسة استرداد وشروط استخدام وسياسة خصوصية وقناة دعم للمستخدمين.
